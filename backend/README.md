# ForteBank backend

Каркас Go-бэкенда для Datathon 26. Сейчас есть структура, места для будущих компонентов и предварительный контракт API. HTTP-сервер, обработчики, менеджеры, хранение и анализ видео ещё не реализованы. `main.go` содержит только объявление пакета: `go run .` и сборка приложения пока не работают.

## Структура

Clean Architecture задаёт границы и направление зависимостей. Singleton описывает время жизни экземпляров. Здесь предусмотрен знакомый подход: один контейнер приложения, внутри него менеджеры и компоненты создаются через `sync.Once`. Сам механизм будет реализован позже, без обязательного глобального контейнера. Контроллеры и worker будут обращаться к сервисам через интерфейсы; детали CV и хранения останутся за границами processors/repositories.

В проектах-образцах используется Fiber v2. Зависимости пока не добавлены. Выбор модели CV, среды её исполнения, БД и очереди остаётся открытым. Модуль `nu-hackathon/backend` — локальное имя, без предположения об адресе удалённого репозитория; директива Go — 1.25.0.

## Swagger

Источник контракта — [docs/openapi.yaml](docs/openapi.yaml). Swagger UI работает отдельным сервисом и не требует реализованного Go-приложения.

Из папки `backend`:

```powershell
docker compose up -d swagger
```

Открыть **http://localhost:8081**. Требуется запущенный Docker Desktop с Linux containers. При первом запуске загружается образ; после загрузки образа просмотр документации не требует интернета. UI использует локальный OpenAPI-файл, внешний validator выключен. Выполнение запросов в UI отключено, пока API не реализован. Для подключения рабочего API позже нужно проверить `servers` в спецификации, разрешить нужные методы в `SUPPORTED_SUBMIT_METHODS` и настроить CORS либо общий origin.

Остановить:

```powershell
docker compose down
```

Проверить конфигурацию без запуска:

```powershell
docker compose config --quiet
```

Те же команды доступны через `make swagger`, `make swagger-down`, `make swagger-config`, если установлен Make. Этот Compose поднимает только документацию.

## Контракт и границы текущего этапа

- `POST /api/v1/analyze`: multipart-поле `file` с видео `.mov`; ответ с `job_id`.
- `GET /api/v1/jobs/{job_id}`: статусы `processing | done | failed`.
- Оба маршрута защищаются `X-API-Key`.
- Завершённый результат: `verdict`, `violations`; для события — тип, время, объяснение и 1–3 JPEG в base64.
- HTTP-коды, формат ошибок, лимит загрузки 64 MiB и внутренний таймаут 270 секунд — предложения команды. В ТЗ они не определены; общий предел проверки жюри — 5 минут.
- Правило и источник обязательны в продукте. Для совместимости с JSON жюри их планируется указывать в `description`; отдельные поля API для них сейчас не добавлены.

Подробности и расхождения внутри задания: [docs/requirements.md](docs/requirements.md). Алгоритмические референсы: [docs/references.md](docs/references.md).

`.env.example` описывает предполагаемые настройки, но ещё не читается приложением. Реальный API-ключ не создавался. Видео, кадры, веса и локальные секреты исключены через `.gitignore`. Dockerfile приложения, SQL-схема, CI/CD и исполняемые проверки появятся вместе с реализацией соответствующих компонентов.

Следующий этап после выбора подхода: определить минимальные интерфейсы CV и хранения, реализовать контейнер, upload/worker/polling, проверку ключа, ограничения ресурсов и остановку процесса. Затем проверить локальную обработку, точность таймкодов и итоговый лимит 5 минут на реальном оборудовании.
